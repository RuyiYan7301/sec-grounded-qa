# v0.4 2c plan: fixes from 2a and 2b, re-measured on fresh data

Written 2026-11-19, before any 2c code change. Protocol from `docs/v0.4-plan.md` section 2c: fixes use what
2a and 2b showed; they are re-measured only on fresh data (accuracy sample seed 2607, drawn from cells not in
the first sample; 160 new generated questions, seed 2608). Results on the first samples after fixing are not
reported as accuracy. Step 2 results (`docs/v0.4-step2-results.md`) stay stated for the pre-2c engine.

## Fixes, in order

1. **Fiscal-year labels (HD, LOW, JNJ).** Each 10-K's own fiscal-year focus (DEI `fy` on the rows filed
   with it, as in `labels.json`) disagrees with the engine label by exactly -1 for every 10-K since 2018 at
   HD (9/9), LOW (9/9) and JNJ (8/8); no other filer has a consistent offset (CRM: 1 of 9, not a pattern),
   and none of the 8 original filers is affected. Fix: a per-filer label offset table derived by a script
   from the DEI focus (offset applied when at least 5 of the filer's 10-Ks since 2018 agree on it), committed
   with its evidence; `facts.fiscal_year` takes the ticker and applies it. Check: the v0.2 test gold for the
   original 8 filers is unchanged byte for byte.
2. **Submissions pagination in `resolve.FilingFactIndex`.** Read the extra submissions pages, as the
   coverage script already does. Check: VZ and WMT see all their 10-Ks since FY2019.
3. **Operating expenses that include cost of sales (GM, CAT).** When a filer's `OperatingExpenses` value
   is within 0.5% of revenue minus operating income and the filer also reports a cost-of-revenue concept,
   the answer carries a scope warning (`opex_includes_cost_of_sales`); the value is not changed, because
   the tag is the filer's own. 
4. **Cost of revenue that is products only (UNH).** Same treatment: a scope warning when the resolved
   concept is `CostOfGoodsAndServicesSold` and it is below 50% of revenue minus operating income for a
   filer with a separately tagged larger cost line. Threshold fixed here, before looking at new cells.
5. **Long-term debt reported as parts only.** When no total concept exists but both the noncurrent and
   current long-term debt parts exist for the same period, report their sum as a derived value with a
   `derived_sum` note naming both facts, instead of not_reported.

Not fixed in 2c: IBM's statements incorporated by reference (a filing-text issue, not the fact store); the
GD debt cell (unresolved); the execution check's extra-period gap (an evaluation issue, handled in the step-2
reward already).
