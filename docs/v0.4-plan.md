# v0.4 plan: 85 companies, FY2019-FY2025, and a distilled planner

Written 2026-11-17, before any v0.4 data is downloaded and before any v0.4 run. The frozen v0.2 engine,
benchmark, scorers and results, and the v0.3 Item 1A results, are not changed. Everything below is
reported as v0.4, separately from them.

Three steps, in this order. Each step's test data is fixed here, before the step starts.

1. **Scale** (week of 2026-11-18): S&P 100 non-financial companies, fiscal years 2019-2025; measure how
   the rules built on 8 companies generalize, before changing them; then fix.
2. **Trained planner** (2026-11-25 to 2026-12-08): fine-tune a small model (LoRA) to produce the typed
   plan, first by supervised distillation, then by reinforcement learning with a reward computed by the
   executor and the frozen scorer; constrained decoding against the plan schema; compare each stage with
   the frozen `qwen3:8b` planner.
3. **MCP server and agent comparison** (week of 2026-12-09): expose the evaluated tools over MCP; compare
   one agent with these tools against the same agent with raw XBRL tools. Its protocol is written as a
   separate plan before step 3 runs; only its outline is here.

**Amendment 2026-11-18** (before any step-2 code or run): step 2 is extended from one week to two, adding
reinforcement learning (section 3b) and constrained decoding (section 3c); step 3 moves one week later and
is reduced (section 4). The company split, test sets and metrics of section 3 are unchanged.

Out of scope for v0.4: natural-language screener, accounting red-flag scores, Item 1A beyond the companies
already cached, a new UI. Possible if time remains (not promised): calendar-aligned peer comparison,
restatement classification. Reasons: `C:/Users/Admin/reports/SEC 分析功能 需求调研.md` (author's notes, not

## 1. Universe and snapshot

- **Source**: Wikipedia "S&P 100" constituents table, revision 1385872457 (2026-11-15T18:41:35Z), copied
  to `data/universe/sp100_rev1385872457.json`. 101 rows.
- **Excluded**: GICS sector Financials (15 rows: AXP BAC BLK BNY BRK.B C COF GS JPM MA MS SCHW USB V WFC).
  Banks and insurers do not report revenue, gross profit or operating income in the form the ontology
  defines. No other exclusion is made after looking at data.
- **Kept**: 86 rows, 85 filers (GOOG and GOOGL are one filer, kept once as GOOGL). Includes Real Estate
  (AMT) and Utilities (DUK NEE SO); metrics they do not report are expected to come out `not_reported`.
- **CIK**: from SEC `company_tickers.json`, saved with its download date. A ticker that does not resolve,
  or resolves to more than one CIK, is listed in the manifest and decided by hand, with the reason written
  down.
- **Years**: fiscal years 2019-2025, each company's own fiscal year, labelled as now (`facts.fiscal_year`).
  Companies with shorter histories (GEV spun off 2024, SNDK 2025, PLTR listed 2020) are kept; their
  earlier years are `out_of_range` for that company, not errors.
- **Snapshot**: unchanged, `SECQA_SNAPSHOT=2026-10-16`. Facts filed later are ignored, as in v0.2.
- **Quarterly facts** are downloaded with the annual ones (they are in the same companyfacts file) and
  kept in the store, but v0.4 does not answer quarterly questions. Quarterly answers need Q4 derivation
  (FY minus 9M), share and EPS exceptions, and new tests; they are a later version.

## 2. Generalization test (run once, before any fix)

The 8 original companies are where the ontology and engine were built. The 77 new companies have never
been looked at. "Frozen" means tag `v0.2-engine-freeze` plus the v0.3 post-hoc commits that do not touch
the numeric engine.

The frozen planner cannot run on new companies: `plan.schema.json` and the planner prompt list the 8
tickers and FY2023-FY2025. So the test has two parts.

### 2a. Data layer (no model)

Question: given a correct plan, does the frozen ontology + executor return the right number for a new
company?

- **Cells**: every (company, metric, fiscal year) for the 77 new companies, 23 metrics, FY2019-FY2025.
- **Coverage report**: for each cell, `answer` / `not_reported` / `out_of_range` / error, and which concept
  answered (primary or fallback). Descriptive, all cells.
- **Accuracy sample**: 150 cells drawn with `random.Random(2604)` from the `answer` cells, stratified by
  metric (at least 5 per metric, rest proportional). For each, the 10-K is read: the value the filing
  reports for that line, and whether the ontology's definition matches what the filing calls it. Outcome
  per cell: `correct`, `wrong_value`, `wrong_concept` (number matches the tag but not the metric's
  definition), `scope` (e.g. includes noncontrolling interests, not stated).
  Also 50 `not_reported` cells (seed 2605): is the item really absent from the 10-K?
- **Reviewer**: a Claude sub-agent given only the filing text excerpt, the metric definition and the
  value; it does not see the engine's concept choice reasoning. This is model review, not human review,
  and is stated with every figure. The project author spot-checks 20 of them.
- **Independent cross-check**: the SEC frames API (one concept, all filers, one calendar period) for the
  primary concept of 6 metrics (revenue, operating income, net income, total assets, operating cash flow,
  EPS diluted), all 85 companies, FY2022-FY2024: agreement with the store's value within 0.5%. Frames
  pick one value per filer by their own rules (latest filed, calendar-aligned), so disagreements are
  listed and explained, not counted as errors automatically.
- **Reported**: correct rate with Wilson 95% interval, by metric and by sector; error types; coverage.
  Also the same sample procedure on FY2019-FY2022 for the 8 original companies (new years for them).
- **What follows**: if the correct rate is below 0.90, step 1 continues with data-layer fixes and step 2
  starts later; it is not shortened.

### 2b. End-to-end QA with the frozen planner prompt

- **Mechanical generalization only**: the ticker list, company names and year list in `plan.schema.json`
  and the planner prompt are generated from the universe instead of hard-coded. Nothing else in the prompt,
  schema, executor or scorer changes. This change is committed and its diff shown before the run.
- **Questions**: `gen_qa.py`'s templates and intent mix, new seed 2606, on new companies only:
  160 generated questions. No handwritten or adversarial layer is written for v0.4 (no time); this is
  stated.
- **Gold** comes from `gold.py` (raw companyfacts with the ontology's concept lists). Gold therefore shares
  the ontology: 2b measures planning and execution, not the ontology's mapping; 2a measures the mapping.
- **Scorer**: the frozen v0.2 scorer. Runs: `qwen3:8b`, same digest and settings as v0.2, once; a 40-item
  rerun for noise.
- **Reported**: final correct with interval, by intent; failure categories; compared with v0.2's
  generated layer (80/80 on 6 companies), noting the different companies and years.

### 2c. Fixes

Fixes are made after 2a and 2b, using what they show, and are tagged v0.4. They are re-measured on fresh
data only: a second 150-cell accuracy sample (seed 2607) drawn from cells not in the first sample, and 160
new generated questions (seed 2608). Results on the first samples after fixing are not reported as
accuracy.

## 3. Distilled planner (protocol fixed now; run in step 2)

Goal: a small model that writes the typed plan as well as `qwen3:8b`, faster and on smaller hardware.

- **Task**: question -> plan JSON (the v0.4 plan schema). Only the planner is replaced; executor, renderer
  and scorer stay the same.
- **Student**: Qwen3-1.7B, LoRA, on the local RTX 5070 (12 GB). Qwen3-0.6B as a second size if time
  allows. Hyperparameters chosen on the validation split only.
- **Company split** (fixed now, by ticker):
  - **test**: AAPL NVDA MSFT AVGO INTC AMD (the v0.2 test companies) and 15 new companies drawn with
    `random.Random(2609)`;
  - **validation**: 8 new companies (same draw, next 8);
  - **train**: all other companies, including CSCO and ORCL.
  No question about a test company is used in training or validation; a test question naming any
  training company too (cross-company comparison) is dropped from training.
- **Training data**: plans come from the generator's gold plans (correct by construction), not from the
  8B model's outputs. Question text: the generator's templates plus paraphrases written by a different
  model family (Claude Haiku), so the student does not only learn template wording. Refusal plans
  (out_of_ontology, out_of_range, not_reported, unsupported) are generated by rule on training companies.
- **Test sets**:
  1. the frozen v0.2 Part A test (160 items, including the 40 handwritten and 40 adversarial ones), with
     the v0.4 schema; these question templates and handwritten wordings are not used in training;
  2. 160 new generated questions (seed 2611) on the 15 new test companies only, using only templates held
     out from training (the template list is split by `random.Random(2610)` before any training: half
     train, half test).
- **Metrics**: final correct (frozen scorer) and plan exact match, each with paired comparison against
  `qwen3:8b` on the same items (McNemar); invalid-plan rate; median latency per plan; GPU memory.
- **Claim allowed**: "the 1.7B planner reaches X of 8B's final-correct on unseen companies and question
  wordings, at Y latency". Not allowed: claims on question types or companies outside the test sets.
- **Gold for training and test** is built with the v0.4 engine after the 2c fixes, so the trained planner
  and the 8B planner are scored against the same gold.

- **Splits written** (2026-11-18, `data/train/v0.4/splits.json`, `secqa.train.splits`): test 21 companies
  (the 6 v0.2 test companies + AMT COP DHR FDX ISRG JNJ LLY LOW MDLZ META MMM PANW T UNH XOM), validation 8
  (BA LIN MU NEE NOW PFE SBUX UPS), train 56. Templates: one train and one test template per key (fact
  lookup: two train, one test).
- **Clarification (2026-11-18, before any training data)**: test set 1 (frozen v0.2 Part A) was generated
  from all templates, so half of its generated items use train-half wording. It is reported overall and
  split by the template half each generated item came from; handwritten and adversarial items are unseen
  wording either way. Training questions use train-half templates and paraphrases of them only; a
  paraphrase that matches a test-half template (after lower-casing and stripping punctuation) is dropped.

- **Training data written** (2026-11-18, before any training; `secqa.train.build_data`): SFT train 3,827
  items (seed 2613, train companies), validation 383 (validation companies), GRPO prompts 1,145 (seed
  2612, train companies, SFT question texts removed). About 13% refusal plans, about 4% not-reported cells
  (answer plan, executor reports absence). Addition not in the original protocol: half of the training
  questions name the metric by an ontology alias instead of its display name (the frozen generator uses
  display names only); aliases come from the ontology, not from any test item. Test set 2 keeps display
  names. Paraphrases that could produce a v0.2 test question were dropped (5 templates).

- **Amendment after the first validation run (2026-11-18; validation only, no test item seen)**: with the
  one-line instruction alone, the SFT model cannot map unseen company names to tickers (validation: 182/383
  plans valid, nearly all failures invented tickers such as "B" for Boeing, "LIND" for Linde). The full 8B
  prompt carries the whole name-to-ticker table, the short one carried none. The short system message
  now adds the companies found in the question by deterministic name and ticker matching
  (`train/common.py: company_hint`, universe short names plus a hand-written list of common names, e.g.
  Google, Exxon), e.g. "Companies mentioned: Boeing = BA; Micron Technology = MU." It finds every gold
  company with no extra one on SFT train and validation, both test sets and the 2b set. The first SFT run
  (`runs/sft_r16_lr2e-4`, without the hint) is kept and reported as the failed design.

- **SFT with the hint, validation result (2026-11-19; validation only)**: same settings as the first run
  except micro-batch 8 with 2 accumulation steps (effective batch 16 unchanged), because two attempts at
  micro-batch 16 ran out of system RAM while another job shared the GPU. 10.6 min, GPU peak 5.3 GB.
  Validation (383): checkpoint-240 383 valid, 369 execution correct, 11 refusals on answerable items;
  checkpoint-480 383 valid, 382 execution correct, 0 refusals on answerable items. The only miss is a
  forecast question ("Model out Starbucks's total net sales for FY2026") refused as out_of_ontology instead
  of unsupported. **Chosen: checkpoint-480**, by validation execution correct, as fixed above.
  Caveat stated now, before any test run: validation uses the same train-half templates and paraphrase
  style as training, on unseen companies only, so it is close to ceiling and says little about unseen
  wording; that is what the two test sets measure. It also leaves GRPO checkpoint selection on validation
  with almost no headroom (1 item), which is reported with the GRPO results.

- **GRPO headroom check (2026-11-19, before any GRPO run; training prompts only)**
  (`train/grpo_headroom.py`, `results/v0.4/planner/grpo_headroom_sft_hint_ck480.json`): SFT checkpoint-480,
  200 GRPO prompts (seed 2614), 8 samples each with TRL's GRPO sampling (temperature 1.0, top_p 1, top_k 0).
  Only 15/200 groups (7.5%) have mixed rewards; 185 are all correct; mean reward 0.986; the median group
  has 1 distinct text (all 8 samples identical). The 20 imperfect rollouts are 13 stray refusals of
  answerable questions and 5 wrong plans. So on these prompts about 92% of groups give GRPO no gradient,
  and the rest would mostly teach "do not refuse at random". GRPO as planned is not run on this prompt
  set; what replaces it is decided next and recorded here before it runs.

- **Amendment: hard-wording GRPO pool (2026-11-19, decided with the user; written before any of this data
  is generated and before any test run of any step-2 arm)**. GRPO trains on prompts where the SFT model is
  not yet certain. New question templates are written by Claude Haiku (as for the SFT paraphrases), from
  the same train-half input (`paraphrase_input.json`), in four styles chosen by me from general knowledge
  of how people ask: (H1) conversational, with a preamble or context sentence; (H2) terse, keyword-like;
  (H3) reordered or multi-sentence (year or company first, the request in a second sentence); (H4) the
  same request said indirectly (e.g. "how much bigger or smaller was ... than ..." for a change), with
  the intent unchanged. Then deterministic surface noise, each independently with probability 0.5:
  lower-casing, dropping the final punctuation, and writing `FY2021` as `FY21` or `FY'21`.
  Filters as for the SFT paraphrases (placeholders must match; no test-half template after normalisation;
  no template that can produce a v0.2 test question), plus no question text already in SFT train,
  validation or the first GRPO set. Companies: train split for the GRPO pool (`grpo_hard`, seed 2615);
  a hard-style validation set on the validation companies (`val_hard`, seed 2616) for GRPO checkpoint
  selection, never test.
  **Gate**: the headroom check (same script and settings, 200 prompts) on the hard pool must give at
  least 25% mixed groups; otherwise GRPO is not run and that is reported.
  Disclosure: I have seen the v0.2 test items (including the handwritten and adversarial ones) and the
  test-half templates. The four styles are generic, but this knowledge may influence them; no test item
  or test template is given to the model that writes the templates.

- **Hard pool built and gate result (2026-11-19)**: `grpo_hard` 1,152 prompts, `val_hard` 383 (11 Haiku
  templates dropped by the v0.2-test filter; gold plans get reward +1 on all items). The company hint
  misses 41 of 1,152 GRPO-hard prompts (lower-cased short names such as "ibm", "rtx": names of 4
  characters or fewer are matched case-sensitively) and none in `val_hard`; the hint is not changed.
  Headroom on the hard pool (200 prompts, seed 2614): **55/200 groups mixed (27.5%) -> gate passed**
  (narrowly, against 25%). Mean reward 0.768; rollouts 1,395 correct, 118 invalid plans, 48 wrong,
  39 refusals of answerable questions; weakest kind percentage-point change (mean reward 0.20 over 23
  prompts). For comparison, the first pool: 7.5% mixed, mean reward 0.986. GRPO now runs on `grpo_hard`
  with checkpoints compared on `val_hard`.

- **GRPO run and checkpoint choice (2026-11-19; validation only, no test item seen)**: `runs/grpo_hard_lr1e-5`,
  1 epoch over `grpo_hard` (288 optimizer steps, 4 prompts x 8 rollouts each), lr 1e-5, beta 0.04, 39 min,
  GPU peak 4.6 GB. On `val_hard` (383), execution correct: SFT 344; GRPO checkpoints 50/100/150/200/250/288:
  365/372/375/375/375/375. Checkpoints 150-288 tie on execution correct; plan exact match 361/360/360/360.
  **Chosen: checkpoint-150** (highest execution correct, then highest plan match; this tie-break is stated
  after seeing the numbers, which differ by one item). SFT vs checkpoint-150, paired on `val_hard`: 32 gained,
  1 lost (exact McNemar p = 7.9e-9). 24 of the 32 gains were invalid SFT plans (mostly terse or lower-cased
  wordings); 8 were wrong SFT refusals. Refusal-rate stop rule: answerable items refused or invalid fell
  from 35 to 2, no rise. Original validation (`sft_val`): 382/383, as SFT (the one miss is again the
  forecast question, now planned as a FY2026 lookup, which the executor refuses as out of range).
  Cost seen on `val_hard`: silent wrong (an answer comes out and is wrong) rose from 3 to 6. Two of the 6
  answer a question that must be refused ("adjusted net income" planned as net income, "third-quarter
  operating income" as operating income), three plan a percentage-point change as a multi-period lookup
  (terse "pp move ..." wording), one reads FY20 as FY2023. Reported with the test results.
  Caveat: `val_hard` uses the same hard templates as `grpo_hard` (different companies), so this shows the
  effect on that wording style; the test sets measure unseen wording.
  Rollouts were not stored by the trainer, so the "30 rollouts read by hand" check is replaced by reading
  the 33 changed `val_hard` items and the 8 remaining failures (above).

## 3b. Reinforcement learning on the executor's verdict (amendment 2026-11-18)

Why it is possible here: a plan can be checked without a person or a reward model. The plan is run by the
deterministic executor and the answer is scored against generated gold by the frozen scorer.

- **Starting point**: the SFT checkpoint of section 3 (chosen on validation), same LoRA setup.
- **Algorithm**: GRPO (group relative policy optimization), as in TRL's `GRPOTrainer` or Unsloth; group size
  8 (4 if memory requires, stated), sampling temperature 1.0, KL penalty to the SFT checkpoint with
  beta = 0.04 (the GRPO paper's value; corrected 2026-11-18 before any run, because TRL's default is
  0, i.e. no KL term). Thinking mode off, as in SFT. Other settings chosen on validation only.
- **Prompts**: new generated questions (seed 2612) on training companies with training-half templates only,
  plus rule-made refusal questions in the generator's proportion. No overlap with the SFT question texts,
  validation companies or any test item.
- **Reward** (fixed now, from the frozen scorer's verdict; no new judgement is added):

  | planner output | reward |
  |---|---|
  | answer scored correct, or the correct refusal | +1 |
  | refuses an answerable question | 0 |
  | answers and is scored wrong, answers a question that must be refused, or wrong refusal category | -1 |
  | plan invalid against the schema, or executor error | -1 |

  A wrong answer costs more than a refusal, matching the engine's rule that refusing beats a silent wrong
  number.

  Correction (2026-11-18, before any training): "scored correct" uses the frozen *execution* check
  (`run_v2.execution_correct`: outcome, result within the frozen tolerances, required warning codes), not
  the rendered-answer scorer. The rendered answer needs one 8B renderer call per rollout, which does not
  fit in the budget, and the renderer is the same for every arm. Final correct (with rendering) stays the
  test metric. The known risk is that the model learns to refuse everything; that is watched, not assumed away.
- **Reward-hacking checks**, reported with results: refusal rate on answerable validation items at every
  checkpoint (a rise of more than 5 points over SFT stops the run and is reported); executor-error rate;
  30 rollouts read by hand at the chosen checkpoint.
- **Budget**: at most 24 GPU hours. Checkpoint every 50 steps; the checkpoint is chosen by validation final
  correct, never by test.
- **Feasibility gate** (first day of step 2, before SFT): CUDA torch environment for the RTX 5070; 50 GRPO
  steps of Qwen3-1.7B + LoRA on dummy data; measure peak GPU memory, peak system RAM (16 GB) and seconds
  per step. If it does not fit at group size 4, or the projected run exceeds the budget, GRPO is moved to a
  lab GPU or dropped; SFT and 3c run as planned and the outcome is stated.
- **Gate outcome and amendment (2026-11-18, before any training)** (`results/v0.4/feasibility/`): with
  the full v0.4 planner prompt (~2.6k tokens) GRPO does not fit (group 8: out of GPU memory; group 4: did
  not finish 5 steps in 10 minutes and was stopped by the host for low system memory). With a one-line
  instruction as the system prompt, group 8 fits (7.9 GB GPU peak, 6.2 s per step, 10.9 GB system RAM).
  Therefore SFT and GRPO train and are evaluated with the short instruction
  (`Return the typed plan for the question as one JSON object.`); the base-model arms B0 and B1 use the
  full planner prompt, since a base model has no other way to learn the schema. Arm S is also run with
  the full prompt if memory allows at inference (stated either way).

## 3c. Constrained decoding (amendment 2026-11-18)

Decoding is restricted to strings valid under the v0.4 plan schema (a JSON-schema grammar, e.g. xgrammar
or outlines; the library is chosen in the feasibility gate). Any schema feature the grammar cannot express
is listed. Measured separately from training, so its contribution is not credited to SFT or GRPO.

Correction (2026-11-18, same day, before any step-2 run): the frozen `qwen3:8b` planner already decodes
under the plan schema (Ollama structured outputs, `format` = the schema) and gets one repair call when
validation fails (`plan.make_plan`). So arm T is constrained, and constrained decoding is not new to the
project; what 3c measures is its effect on the small model. For parity every 1.7B arm also gets the same
one repair call with the same repair prompt.

**Amendment 2026-11-18 (after reading the 10 renderer losses of 2b; before any step-2 test run, any GRPO
code, and any GRPO run)**:
- *Secondary final-correct count.* The frozen scorer counts an earlier-reported value quoted as provenance
  as a contradiction (5 of the 10 2b renderer losses, `docs/v0.4-generalization.md`). The frozen 2.1 count
  stays primary. Next to it every arm also reports a secondary count from `evaluation/v4/provenance.py`:
  the frozen `score_item` on an answer in which a number is masked only if it equals an earlier value
  recorded in that item's own execution result and its sentence has a provenance cue; restated-value
  questions are not masked. On the 2b run it changes 144 to 149 (exactly the 5 items I had read as false
  positives) and on the v0.2 test run it changes nothing (145, 0 items masked). The rule was written
  after seeing these items, so its agreement with my reading is not a validation of it; it is fixed from
  now on and not tuned on any step-2 output.
- *GRPO reward, restated-value questions.* The execution check compares result values only, so a plan
  with an extra period can be scored correct (2b item 135: FY2024 added to a FY2019 question). For the
  GRPO reward, a restated-value plan also needs its period set to equal the gold period set; otherwise it
  counts as a wrong answer (-1). The eval metric is unchanged; every arm reports how many of its
  restated-value plans carry extra periods.

## 5. Constraints

- EDGAR: at most 10 requests per second (client uses 4/s), declared User-Agent set by the author in
  `.env`; ~85 companyfacts + submissions files, plus 10-K text for the accuracy sample only.
- Windows machine has 16 GB RAM: no model runs during data download; one model process at a time.
- Local torch is CPU-only; CUDA torch for the RTX 5070 (sm_120) is installed in a separate environment
  before step 2. During GRPO no other model process runs on the machine.
